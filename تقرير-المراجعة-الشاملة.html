3. ما تم إصلاحه والتحقّق منه

عالية F1 — تبويب Agents كان يُسقط لوحة التحكم بالكامل (شاشة بيضاء)

الحالة: مُصلَح ومُتحقَّق منه في المتصفح · الملف: apps/web/src/App.tsx

ما حدث فعليًا: عند فتح تبويب Agents رمى React خطأً غير مُلتقط فأزال الشجرة كلها:

[error] Error: Objects are not valid as a React child
        (found: object with keys {name, level, experience, experienceToNextLevel})
    at AgentsView (http://localhost:5173/src/App.tsx)
[error] The above error occurred in the <span> component
[error] Warning: Encountered two children with the same key …
        at AgentsView (App.tsx)   ← مفتاح React مكرّر

السبب الجذري: الـ API يعيد skills كسجلات {name, level, experience, experienceToNextLevel} (مؤكَّد من GET /api/v1/agents)، بينما AgentsView كان يعاملها كـ string[] ويعرضها مباشرة (<span key={s}>{s}</span>). فسقط العرض، والأسوأ: لا يوجد أي Error Boundary، فخطأ في لوحة واحدة يُفرِّغ الصفحة بأكملها (بدليل أن نص الصفحة صار فارغًا في كل تبويب بعد فتحها).

الإصلاح:

  • دالة skillNames() تُطبِّع المهارات (سلسلة أو سجل) وتُزيل التكرار — فتصبح مفاتيح React فريدة والعارض آمنًا مهما كان شكل الـ DTO.
  • <ViewErrorBoundary key={section}> يحيط بالمحتوى: فشل عرض واحد لم يعد يُسقط الهيكل، ويُظهر رسالة الخطأ وزر «إعادة المحاولة»، ويتصفّر عند تغيير التبويب.

4. نتائج مُبلَّغة تحتاج قرارك (لم أُغيِّر سلوكًا تصميميًا)

متوسطة F3 — الوكيل «الجائع» يقترح راحة يرفضها المدقّق: 653 محاولة مهدورة في ~2.5 ساعة

الأدلة: packages/simulation/src/decision.ts:107 · packages/simulation/src/actions.ts:213 · سجل الـ API

محرك القرار يقترح REST عندما needs.HUNGER <= CRITICAL، لكن مدقّق الأفعال يرفضه لأن الحالة الحالية WORKING لا يُسمح لها بالانتقال إلى حالة الراحة: 

WARN Decision rejected by the action validator
     decision: "REST"  reason: "Hunger low (0); taking a restorative break"
     error: "Cannot start REST from state WORKING"
     → 653 تكرارًا في ~2.5 ساعة (التبويب Simulation يعرض Critical: HUNGER, SOCIAL)

الأثر: الوكيل العامل لا يأخذ راحته أبدًا مع بقاء الحاجة حرجة، وكل نبضة تُهدَر، والسجل يُغرق بتحذيرات متطابقة. التوصية: إمّا أن يقترح المُقرِّر مسارًا مشروعًا (STOP_ACTIVITY → IDLE → REST)، أو أن يقفل القرار على آلة حالات الوكيل، مع تسجيل الرفض المكرّر بمعدّل محدود. لم أنفّذها لأنها قرار تصميمي (هل يهجر الوكيل مهمته ليرتاح؟) ويجب أن يُغطّى بتعديل اختبارات المحاكاة.

متوسطة F4 — التفويض بدور عام لا بنطاق الشركة (عزل مستأجرين)

الأدلة: packages/security/src/rbac.ts (تعليق التصميم) · apps/api/src/routes/company.routes.ts:37

OWNER/ADMIN/OBSERVER أدوار عامة لا ترتبط بعضوية شركة: GET /companies يعيد listCompanies(prisma) (كل الشركات)، وGET /companies/:id يعيد أي شركة لأي مستخدم مُصادَق. أي OBSERVER يقرأ محافظ وسجلات وأحداث كل الشركات.

الملف نفسه يوثّق أن هذا اختيار واعٍ لـ Phase 1 («Deliberately coarse… Phase 1 has exactly one human account model»). التوصية: إمّا ربط الصلاحيات بعضوية CompanyMember، أو تقييد الواجهة الحالية بمستخدم واحد وتصريح ذلك في docs/SECURITY.md. (نقطة إيجابية: هذا تحدٍّ قائم على دور، وليس تخمينًا — كل كتابات الطلب تمرّ بـ principalToActor.)

منخفضة F5 — انحراف في شارة التوثيق: «267 اختبارًا» والفعلي 263

الأدلة: README.md:23 · scripts/check-doc-counts.ts

الشارة تعلن 267_passing والقياس الفعلي 292 ناجحًا (307 إجمالًا و15 مُتخطّى بيئيًا). لاحظ أن الرقم نفسه يتغيّر بين الجولات (الأجنحة المتخطّاة مثل Docker/opencode تتوقف على البيئة)، ولهذا يستثني حارس التوثيق scripts/check-doc-counts.ts أعداد الاختبارات عن قصد — فالانحراف لا يُكتشف آليًا. التوصية: حذف الرقم من الشارة والاكتفاء بحالة البوابة (أو تحديثه في كل تغيير، وهو ما سيظل ينحرف).

منخفضة F6 — 198 ملف قاعدة بيانات اختبارية بحجم 213MB متروكة

الأدلة: ls database/test-*.db | wc -l → 198 · du -sh database → 213M

الأسماء نمط test-<pid>-<token>.db تشير إلى قواعد مؤقتة لا تُنظَّف بعد التشغيل. مُهمَلة في git (database/*.db) فلا تتسرب للمستودع، لكنها تُثقل القرص وتبطئ أي مسح للمجلد. التوصية: تنظيف في afterAll أو أمر npm run db:clean.

منخفضة F7 — تدفّق OAuth: مقارنة HMAC غير ثابتة الزمن + حالة في ذاكرة العملية

الأدلة: packages/connectors/src/oauth.ts:93–101

التوقيع يُقارَن بـ !== (مقارنة غير ثابتة الزمن)، وpendingStates خريطة داخل ذاكرة العملية — فمع أكثر من نسخة API واحدة تفشل عمليات callback عشوائيًا. الجانب القوي: الحالة مُوقَّعة، أحادية الاستخدام، ولها انتهاء صلاحية. التوصية: timingSafeEqual + مخزن مشترك (جدول Prisma) للحالة.

معلوماتية F8 — نقطتان للتوثيق لا للتعديل

  • GET /api/v1/mcp/ غير مُصادَق ويعرض أسماء أدوات MCP (كشف معلومات بسيط). الطلب الفعلي POST / يرفض بدون مفتاح API (packages/mcp/src/server.ts:561).
  • تبويب Performance يحتاج >4 ثوانٍ للرسم الأول (تحميل lazy + جلب بيانات)؛ ظهر «Loading…» في الانتظار القصير وسليمالعرض بعد 8 ثوانٍ — ليس عيبًا، لكنه قابل للتحسين.

6. نقاط قوة مُتحقَّق منها (لا مجاملة)

  • التغطية الأمنية للمسارات كاملة: 29 ملف مسار — كلها تستخدم authenticate وrequirePermission، عدا ثلاث حالات مقصودة: auth (دخول)، وevents (يتحقق من الرمز بنفسه ويشترط event.read)، وmcp (مفتاح API)، وoauth/callback (حالة موقّعة).
  • لا SQL خام: الاستعلام الوحيد $queryRaw هو SELECT 1 لفحص الصحة — لا بناء جمل بالإدخال.
  • تصلّب النقل: helmet، CORS بقائمة أصل مسموح، حدّ معدّل عام، وtrust proxy بعدد قفزات صريح (لا انتحال X-Forwarded-For).
  • فشل صريح في الإنتاج: config.ts يرفض الإقلاع إذا كان JWT_SECRET افتراضيًا أو أقصر من 32 حرفًا، أو كلمة مرور seed الافتراضية — لا «تحذيرات تُتجاهل».
  • الـ ledger هو الكاتب الوحيد: قيود immutability + قفل تفاؤلي، وverifyLedger() يُستخدم فعليًا في tests/finance.test.ts وtests/ai-platform-integrity.test.ts.
  • الأدوات والصلاحيات: كل فعل وكيل يمرّ بـ ToolExecutor (تدقيق كل نتيجة، بما فيها الرفض)، ومسار الخروج عن مجلد العمل مُختبر في المتصفح والاختبارات.
  • لا dangerouslySetInnerHTML في الواجهة، والرمز يُحفظ في sessionStorage (يُمسح بإغلاق التبويب) لا في localStorage.

8. المنهجية والقيود

  • المنهجية: تعداد المسارات ومقارنة الحرّاس برمجيًا، فحص أنماط الخطر (SQL خام، XSS، أسرار، صلاحيات)، ثم تشغيل التطبيق فعليًا وسياقة كل تبويب مع رصد console/page errors ولقطات، ثم إصلاح الجذر وإعادة التحقق في جلسة متصفح جديدة.
  • لم أُنفّذ: تدفّق مصنع كامل حتى الـ PR/Merge (GitHub token غير مهيأ: factory.githubConfigured=false)، ولا نشرًا إنتاجيًا، ولا db:reset/إعادة تهيئة البيانات، ولا أي أمر مدمّر.
  • جاهزية الإنتاج لم تُختبر ضد بيئة إنتاج حقيقية؛ أحكام الإنتاج مبنية على قراءة الشيفرة وليس على نشر فعلي.
  • عيب المحاكاة (F3) مُبلَّغ لا مُصلَح لأنه قرار تصميمي؛ F4–F7 تحتاج قرارك قبل التعديل.
