3. الضمانات المحاسبية (Ledger)

  • Atomicity — تحديث الرصيد + قيد Transaction في transaction واحدة.
  • No overdraft — رصيد سالب مرفوض.
  • Double entry — التحويل يكتب DEBIT + CREDIT يشتركان في transferGroupId.
  • Idempotency — idempotencyKey يحوّل إعادة المحاولة إلى no-op.
  • Immutability — triggers ترفض أي UPDATE/DELETE على Transaction.
  • Optimistic locking — كل كتابة تتحقق من version للمحفظة.
  • Lock order ثابت — ترتيب محفظات مرتّب، مستحيل الـ deadlock.
verifyLedger() يعيد تشغيل الدفتر كله ويثبت أن كل رصيد مخزّن يساوي مجموع قيوده.

5. قرارات المعمارية ولماذا

  • Monorepo + tsc single-pass — استيراد نسبي بامتداد .js صريح حتى يعمل runtime بعد إصدار dist/.
  • Money وحدات صحيحة — لا float إطلاقاً؛ مخلوط العملات يرمي خطأ؛ حد 2,147,483,647 = 21,474,836.47 KW (مسار الترقية: BigInt/Postgres).
  • SQLite للمرحلة 1 — لا enum ولا Json في موصل SQLite، لذا أعمدة String تتحقق بـ Zod.
  • الدفتر هو الكاتب الوحيد — ledger.service.ts المسار الوحيد الذي يلمس Wallet.balanceMinor.
  • الوكلاء مُهيّؤون لا مُبرمَجون — السلوك من RoleProfile، والسجل يرفض أي دور يمنح صلاحية human-only.
  • الوكلاء يتصرفون عبر الأدوات فقط — الـ runtime لا يملك handle لقاعدة البيانات؛ كل تأثير يمر بـ ToolExecutor.
  • طبقة AI قابلة للاستبدال فعلاً — تغيير المزود = UPDATE وليس نشر جديد.
  • العنونة بالدور لا بالاسم — message.send({to:"EXECUTOR"}).
  • ساعتان — ساعة جدارية للأمان/التدقيق، وساعة محاكاة للوكلا. تمرير الوقت لا يمرّر نوافذ الموافقة.
